# 1. PRD

## 개요

### 한 줄 정의

Smart Journey(스마트 저니)는 줄은 폰도 서지만 "우리 일행이 몇 명이고 지금 도착해 내렸다"는 사실은 차만 증명할 수 있다는 점에서 출발한 서비스이다. 차량 좌석 센서로 탑승 인원을 자동 제안하고, 순정 내비게이션의 실시간 ETA와 매장 대기시간을 맞춰 골든타임에 원격 웨이팅을 접수하며, 도착 후에는 도착 이벤트, 정차, 도어, 좌석 변화를 종합해 "N명 중 M명 하차 확인"을 매장에 자동 전달하는 인카(In-Car) 웨이팅 컨시어지이다.

### 제품 목표

① 폰이 알 수 없는 차량 내부 정보(탑승 인원, 도착, 하차)를 웨이팅의 입력과 인증으로 사용한다. ② 좌석 점유 센서로 탑승 인원을 자동 제안하고 다음 경유지 출발 시 인원 변동을 반영한다. ③ 순정 내비 실시간 ETA와 매장 예상 대기시간으로 호출이 도착 직후(주차·보행 여유 포함)에 오도록 골든타임을 산출하고, 대형 단일 승인 카드와 음성 승인으로 접수한다. ④ 도착 이벤트, 정차, 도어, 좌석 변화를 종합해 하차 인원을 매장 웹 POS에 자동 전달한다. ⑤ 주행 중에는 입력 조작을 잠그고 음성 중심으로 사용해 시선 분산을 줄인다.
기대효과: (1) 운전자·동승자: 인원 입력과 도착 인증 조작이 줄고, 주행 중 폰 조작 없이 승인 한 번으로 끝난다. (2) 가맹점(B2B): 예약금 없이도 차량이 확인한 도착과 인원 정보를 받아 노쇼를 줄이고 테이블을 정확한 인원으로 미리 준비한다. (3) 생태계: 초기에는 로컬 인기 매장에 경량 웹 POS를 무상 보급해 가맹점을 확보하고, 이후 전기차 충전소 대기열, 호텔·백화점 발렛 출차 준비, 드라이브스루 ETA 기반 조리 시작으로 확장한다.

### 배경

원격 줄서기는 이미 보편화되었고, 기존 서비스도 상당 부분을 해결한다. TMAP은 2024년 캐치테이블과 제휴해 내비 앱에서 웨이팅을 걸고 실시간 대기시간과 예상 이동시간을 비교하게 했다. 테이블링은 원격 줄서기, 위치 인증 또는 대기확정코드 입력의 도착 인증, 순서 미루기(매장당 최대 3회)를 제공하고, 캐치테이블은 웨이팅 미루기(매장당 최대 2회)를 제공한다. 그러나 이 서비스들은 운전자가 직접 보고 직접 접수해야 하고, 인원은 수동 입력이며, 도착은 폰 위치나 코드로만 확인하고 실제 몇 명이 왔는지는 알지 못한다. 너무 일찍 줄을 서면 도착 전 호출로 순번이 자동 취소되고 너무 늦으면 도착 후 차 안에서 기다리는 타이밍 문제도 운전 중 조작으로 해결해야 한다. 공모 분야는 현대자동차·기아 Pleos App Market의 모빌리티 라이프 케어(패밀리·동승자 케어 연계)이다.

## 문제 및 해결 방안

### 사용자 문제

1. 타이밍 실패: 줄을 언제 서야 할지 운전자가 ETA와 대기시간을 암산해야 하며, 조기 호출로 자동 취소되거나 도착 후 대기하게 된다.
2. 반복 입력: 웨이팅마다 인원수를 직접 입력해야 하고, 식사 후 일행이 줄어도 다음 매장에 반영되지 않는다.
3. 도착 확인의 번거로움: 도착했다는 사실을 앱의 위치 인증이나 코드 입력으로 따로 알려야 한다.
4. 안전: 이 모든 조작이 주행 중 스마트폰 조작과 시선 분산으로 이어진다.

### 해결 방안

차량만이 알고 있는 정보를 웨이팅의 입력과 인증으로 쓴다.
(1) 좌석 센서 기반 인원 자동 제안: Seat.getCurrentSeatOccupancy(area)가 좌석 영역별 점유 Boolean을 돌려주므로 점유 영역 수를 합산해 인원을 제안한다. 센서는 사람 수만 추정하며 성인·유아를 구분하지 않으므로 정차 중 수정할 수 있게 한다.
(2) 골든타임 원격 웨이팅: 실시간 ETA(TripSummary, onTripInfo)와 매장 대기시간으로 호출이 도착 직후에 오는 시점(남은 ETA = 대기시간 − 도착 여유 10분)을 계산해 대형 단일 승인 카드와 음성 안내로 알리고, 승인 시 접수한다.
(3) 차량 신호 기반 도착·하차 확인(핵심 차별 기능): 도착 이벤트(onDestinationArrived, onWayPointArrived), 정차 상태, 도어 열림·닫힘(Door), 접수 인원 대비 좌석 점유 감소를 종합해 "N명 중 M명 하차 확인"을 웹 POS에 자동 전달한다.
(4) 보조 기능: 정체·대기열 변동 시 순번 미루기 또는 차순위 경유지 선방문 제안, 최대 3곳 코스 일괄 입력.
시스템 구성은 차량용 앱(Pleos Connect, Kotlin) ↔ 클라우드 중계 서버(FastAPI + WebSocket) ↔ 매장 점주용 웹 POS(React, 태블릿)의 3-Tier 구조이다. 사용 SDK·API는 NaviHelper v3.0.5(requestRouteWithWaypoints, requestTrip, TripSummary, NaviHelperEventListener의 onDestinationArrived·onWayPointArrived), Vehicle SDK(Seat, Door), Gleo App Schema(optimizeDailyRoute, registerGoldenTimeWaiting, checkWaitingStatus), 카카오모빌리티 다중 경유지 API와 SK T MAP API, AAOS CarUxRestrictionsManager이다.

### 차별점

기존 웨이팅·내비 서비스가 이미 하는 일(ETA와 대기시간 비교, 도착 인증, 순번 미루기)은 차별점으로 내세우지 않는다. 폰이 알 수 없는 정보, 즉 차량 안에서 실제로 일어나는 일을 쓴다.

| 순간 | 폰 앱 | 스마트 저니 | 사용 차량 신호 |
| --- | --- | --- | --- |
| 접수 | 인원수를 직접 입력 | 좌석 점유로 인원 자동 제안 | 좌석 점유 (Seat) |
| 이동 중 | 인원 변동 반영 불가 | 다음 매장 출발 시 점유 인원으로 갱신 제안 | 좌석 점유 (Seat) |
| 도착 | 위치 인증 또는 코드 직접 입력 | 도착 이벤트, 정차, 도어, 좌석 비움을 종합해 하차 인원 자동 전송 | 내비 도착 이벤트, 주행 규제 상태, 도어 (Door), 좌석 (Seat) |

하차 확인은 인원 수 확인이며 사람의 신원 인증이 아니다. 또한 상용 웨이팅 플랫폼이 서드파티에 공개 API를 열지 않은 한계를 3-Tier 구조(차량 앱, 중계 서버, 웹 POS)로 해결해 실제 동작하는 엔드투엔드 시연이 가능하다.

## 타겟 및 시나리오

### 타겟 사용자

1차 타겟은 Pleos Connect가 탑재된 차량(더 뉴 그랜저, 디 올 뉴 아반떼)으로 주말에 2곳 이상을 방문하며 인기 매장을 이용하는 운전자와 동승자(가족·친구)이다. 동승자는 정차 중 코스 선택과 일정 확인을 보조한다. 2차 타겟(B2B)은 원격 줄서기 노쇼와 호출 취소로 손실이 있는 로컬 인기 매장 점주(웹 POS 사용 가맹점)이다. 패밀리·동승자 케어가 필요한 사용자를 우선 고려한다.

### 사용자 시나리오

[장면 1: 정차] 운전자와 동승자 3명, 총 4명이 탑승하면 좌석 센서가 "오늘의 탑승 인원: 4명"을 제안한다. 동승자가 A 맛집(경유지)과 B 카페(목적지)를 선택하면 앱이 방문 순서를 제안하고 승인 시 순정 내비에 한 번에 입력해 안내를 시작한다.
[장면 2: 주행] A 맛집까지 60분, 예상 대기 30분이다. 출발 40분 뒤 남은 ETA가 20분(대기 30분 − 도착 여유 10분)이 되면 음성 안내와 함께 "지금 A 맛집(4명) 웨이팅을 등록할까요?" 대형 단일 승인 카드가 표시되고, 터치 또는 음성 승인 시 접수된다. 접수 30분 뒤 호출이 오지만 차는 그보다 10분 먼저 도착한다.
[장면 3: 주행] 정체로 도착이 15분 늦어질 것 같으면 ETA와 대기시간을 다시 계산해 "도착이 15분 늦어집니다. 순번을 한 번 미룰까요?"를 제안하고, 승인 시 순번이 조정된다.
[장면 4: 도착] A 맛집에 도착해 정차하고 도어가 열리며 좌석 점유가 4명에서 1명(운전자)으로 줄면 앱이 "3/4명 하차 확인"을 웹 POS로 보낸다. 점주 화면에 "도착, 3/4명 하차, 입장 가능"이 표시되어 점주가 호출하고, 동승자는 번호표 QR로 입장한다. 운전자는 주차 후 합류한다.
[장면 5: 이동] 식사 후 일행 1명이 먼저 귀가하고 3명이 다시 탑승하면 "B 카페 인원을 3명으로 바꿀까요?"를 제안하고, 승인 시 B 카페 대기열에 3명으로 반영한다.

## 성공·위험 요소

### 핵심 지표

운전자 시간 절약: 도착 후 대기 0분 즉시 입장 비율. 서비스 정확도: 골든타임 알림 정확도(호출 전 도착 비율), 노쇼(자동 취소) 발생률, 센서 기반 인원 제안 수락률과 수동 수정 비율, 하차 확인 정확도. 가맹점 가치: 스마트 저니 경유 웨이팅의 노쇼율과 일반 원격 줄서기 대비 비교. 주행 안전: 단일 승인(원클릭·음성) 처리 비율과 주행 중 조작 횟수. 개발·심사 지표: Phase별 산출물(APK, GitHub, 시연 영상) 제출 완료와 2차 오프라인 PT 라이브 데모 성공 여부.
사업 목표 가정(검증 전, 탑재 차량 10,000대 기준): 설치율 20%(2,000대), 월 1회 이상 사용 50%(MAU 약 1,000), 첫 사용 후 30일 내 재사용 목표 40%, 3개월 내 25%. 실제 Pleos 탑재 차량 수는 확인하지 못했으며 확보된 실적이 아니다.

### 리스크

- 상용 웨이팅 플랫폼(캐치테이블·테이블링 등)은 공개 API가 없어 직접 연동하지 않고 자체 중계 서버와 웹 POS로 대체한다. 실제 제휴는 이후 과제이다.
- 좌석 센서는 사람 수만 추정하며 성인·유아를 구분하지 못하고 짐으로 인한 오탐이 있을 수 있다. 정차 중 수정 기능을 제공한다.
- 하차 확인은 인원 수 추정이며 신원 인증이나 보안 용도로 쓰지 않는다. 운전자가 차에 남는 경우를 고려해 M/N 형식으로 표시한다.
- 주행 중 사용 가능 여부는 Pleos 주행 규제 정책과 앱 심사 기준에 따라 제한될 수 있다. Distraction Optimization(DO)을 선언하지 않은 앱은 주행 중 사용이 허용되지 않으므로 주행 중 흐름은 음성 중심으로 설계하고 앱 카테고리와 DO 선언 범위를 확정해야 한다.
- 차량 제어(Vehicle Control) SDK와 TextToSpeech SDK는 현재 "준비 중"이라 신청할 수 없다. 앰비언트 라이트 제어는 선택 기능으로 두고 음성 안내는 Gleo 범위에서 구현한다.
- 정차 판별용 기어 조회(getCurrentGearSelectionState)는 deprecated이다. CarUxRestrictions를 기본으로 쓰고 기어는 보조 조건으로만 쓴다. DrivingMode는 주행 모드·크루즈 정보라 정차 판별에 쓰지 않는다.
- 경유지는 SDK 제한상 최대 2개이므로 한 번에 입력하는 코스는 최대 3곳이다.
- Vehicle SDK 지원 여부는 차량 모델에 따라 다르므로 checkXXXCapabilities로 확인한다.
- ETA와 대기시간 오차로 호출 전 도착이 보장되지 않을 수 있어 재계산과 도착 여유 설정으로 줄인다.
- 위치·인원·웨이팅 정보가 외부 서버로 전송되므로 고지와 동의, 데이터 최소화가 필요하다.
- 제출 리스크: 공식 접수양식을 appdevchallenge@hyundai-partners.com으로 2026.11.15 23:59까지 제출해야 하며, 작품 소개, GitHub 커밋 작성자·프로필·코드 주석, 영상 업로드 계정에 실명·소속·연락처가 노출되지 않아야 한다.

# 2. 기능명세서

## 요구사항 1. 탑승 인원 인식 및 코스 설계

정차 상태에서 좌석 센서로 탑승 인원을 자동 제안하고, 다음 경유지 출발 시 인원 변동을 반영하며, 방문할 여러 목적지(최대 3곳)의 방문 순서를 정해 순정 내비게이션에 일괄 입력하는 기능 영역이다.

### 기능 1.1 좌석 센서 기반 탑승 인원 자동 제안

Seat.getCurrentSeatOccupancy(area)로 좌석 영역(SeatArea)별 점유 Boolean을 읽어 점유 영역 수를 오늘의 탑승 인원과 웨이팅 인원수로 제안한다. 센서는 사람 수만 추정하므로 성인·유아를 구분하지 않으며, 정차 중 수정할 수 있다.

**기능의 근거**: 기존 웨이팅 앱은 등록 때마다 인원수를 수동 입력해야 해 번거롭고 주행 중에는 위험하다.

**성공 기준**: 인원 제안 수락률과 수동 수정 비율을 측정한다.

#### 개발 준비 슬롯

**선행조건**

- 좌석 점유 기능을 지원하는 차량이어야 한다. (checkSeatOccupancyCapabilities로 확인)
- CAR_SEATS 권한이 선언되어 있어야 한다.

**트리거**

- 운전자와 동승자가 탑승해 서비스를 실행한다.
- 좌석 점유 상태가 변경된다.

**동작**

- 좌석 영역별로 getCurrentSeatOccupancy를 호출해 점유 여부를 읽는다.
- registerSeatOccupancy로 변경을 실시간 수신한다.
- 점유 영역 수를 합산해 탑승 인원으로 제안한다.

**결과**

- 오늘의 탑승 인원이 제안되고 승인된 값이 웨이팅 인원수로 사용된다.

**예외**

- 센서를 지원하지 않거나 값을 읽지 못하면 수동 인원 입력으로 전환한다.
- 센서 값과 실제 인원이 다르면 정차 중 수정한다. (짐으로 인한 오탐 가능)

**표시**

- "오늘의 탑승 인원: N명"을 정차 상태 화면에 표시한다.

**권한 & 접근**

- 운전자와 동승자가 확인하고 정차 중 수정할 수 있다. 주행 중에는 수정을 잠근다.

**비즈니스 규칙**

- 센서 산출값은 제안값이며 사용자가 수정한 값이 우선한다.
- 성인·유아를 구분하지 않는다.

**데이터**

- 탑승 인원, 좌석 영역별 점유 여부, 산출 시각, 수동 수정 여부를 저장한다.

### 기능 1.2 다중 목적지 최적화 및 순정 내비 일괄 입력 (보조 기능)

사용자가 선택한 방문지(최대 3곳)의 영업시간, 체류시간, 대기시간, 이동시간을 반영해 방문 순서를 제안하고, requestRouteWithWaypoints()로 순정 내비의 목적지와 경유지에 일괄 입력한다.

**기능의 근거**: 경로 앱과 매장 대기시간 앱이 분리되어 경유지를 수동으로 계획·재입력해야 한다. 차량 고유 기능은 아니므로 보조 기능으로 둔다.

**성공 기준**: 코스 생성 소요 시간, 제안 순서 수락률, 내비 반영 성공률을 측정한다.

#### 개발 준비 슬롯

**선행조건**

- 방문지가 2곳 이상 3곳 이하로 선택되어야 한다. (경유지 최대 2개 + 목적지 1개)
- NAVI_ROUTE_SEARCH 권한과 인터넷 연결이 필요하다.

**트리거**

- 정차 중 사용자가 방문지를 선택하고 코스 생성을 요청한다.

**동작**

- 카카오모빌리티 다중 경유지 API와 T MAP API로 장소 간 소요시간을 계산한다.
- 영업시간, 체류시간, 대기시간을 반영해 순서를 제안한다.
- 승인된 순서를 requestRouteWithWaypoints()로 입력하고 결과를 NaviHelperEventListener로 확인한다.

**결과**

- 방문 순서가 확정되고 내비 안내가 시작된다.

**예외**

- 경로 API 실패 시 입력 순서대로 안내하고 사유를 알린다.
- 영업 종료 장소는 제외하거나 대체 후보를 제안한다.

**표시**

- 제안 순서와 장소별 예상 도착·대기·체류 시간을 요약 표시한다.

**권한 & 접근**

- 코스 설정은 정차 중에만 허용한다.

**비즈니스 규칙**

- 순서 변경은 사용자 승인 후에만 내비에 반영한다.

**데이터**

- 방문지 목록, 영업시간, 체류시간, 소요시간, 순서, 내비 요청 결과를 저장한다.

### 기능 1.3 경유지 출발 시 인원 변동 반영 제안

다음 방문지로 출발하기 전 좌석 점유 수가 직전 접수 인원과 달라졌으면 다음 매장의 인원수를 갱신할지 제안하고, 승인 시 반영한다.

**기능의 근거**: 식사 후 일행 일부가 먼저 귀가하는 등 인원이 바뀌어도 폰 웨이팅 앱은 이를 알지 못한다.

**성공 기준**: 인원 변동 제안 수락률과 수정 비율을 측정한다.

#### 개발 준비 슬롯

**선행조건**

- 다음 방문지에 웨이팅이 예정되어 있거나 접수된 상태여야 한다.

**트리거**

- 경유지 출발 전 정차 상태에서 좌석 점유 수가 직전 접수 인원과 달라진다.

**동작**

- 점유 수가 안정화 시간 동안 유지되면 새 인원수를 확정 후보로 만든다.
- "B 카페 인원을 3명으로 바꿀까요?" 제안 카드를 표시한다.
- 승인 시 중계 서버를 통해 다음 매장의 접수 인원을 갱신한다.

**결과**

- 다음 매장 대기열에 변경된 인원이 반영된다.

**예외**

- 점유 값이 불안정하면 제안하지 않는다.
- 갱신이 거절되면 기존 인원을 유지하고 안내한다.

**표시**

- 변경 전후 인원과 대상 매장을 표시한다.

**권한 & 접근**

- 운전자와 동승자가 정차 중 승인한다.

**비즈니스 규칙**

- 사용자 승인 없이 인원을 바꾸지 않는다.

**데이터**

- 변경 전후 인원, 점유 안정화 시각, 승인 여부, 결과 상태를 저장한다.

## 요구사항 2. 골든타임 원격 웨이팅 트리거

내비 실시간 ETA와 매장 예상 대기시간을 비교해 호출이 도착 직후에 오도록 접수 시점(골든타임)을 산출하고 알리는 기능 영역이다.

### 기능 2.1 ETA·대기시간 기반 골든타임 산출 및 알림

NaviHelper의 실시간 남은 ETA와 매장 예상 대기시간을 비교해 남은 ETA가 (예상 대기시간 − 도착 여유, 기본 10분) 이하가 되는 시점을 골든타임으로 계산하고, 도달 시 대형 단일 승인 카드와 음성 안내로 알린다. 접수 처리는 별도 기능이다.

**기능의 근거**: 너무 일찍 줄을 서면 도착 전 호출로 자동 취소되고 너무 늦으면 도착 후 오래 대기하므로 시점 계산 자동화가 필요하다.

**성공 기준**: 골든타임 알림 정확도(호출 전 도착 비율)와 도착 후 대기 0분 입장 비율을 측정한다.

#### 개발 준비 슬롯

**선행조건**

- 내비 경로 안내가 진행 중이어야 한다.
- 대상 매장의 예상 대기시간을 수신할 수 있어야 한다.
- NAVI_ROUTE 권한이 필요하다.

**트리거**

- 남은 ETA가 (예상 대기시간 − 도착 여유) 이하로 내려간다.

**동작**

- requestTrip과 onTripInfo(TripSummary)로 실시간 ETA를 수신한다.
- 중계 서버에서 매장 대기시간을 갱신 수신한다.
- ETA와 대기시간이 바뀔 때마다 조건을 재계산한다.
- 조건 도달 시 승인 카드를 호출하고 음성 안내를 낸다. 앰비언트 라이트는 차량 제어 SDK를 사용할 수 있을 때만 추가한다.

**결과**

- 골든타임이 산출되고 도달 시 알림이 노출된다.

**예외**

- ETA나 대기시간 수신이 끊기면 마지막 값을 표시하고 재수신 상태를 알린다.
- 이동 시간이 이미 (대기시간 − 여유)보다 짧으면 즉시 알린다.

**표시**

- 남은 ETA, 매장 대기시간, 골든타임까지 남은 시간을 표시한다.

**권한 & 접근**

- 운전자가 알림을 확인하며 알림 설정은 정차 중에만 변경한다.

**비즈니스 규칙**

- 도착 여유 기본값은 10분이며 매장별로 조정할 수 있다.
- 예: 이동 60분, 대기 30분이면 남은 ETA가 20분이 되는 시점(출발 40분 후)에 알린다. 접수 30분 뒤 호출, 도착은 20분 뒤이므로 호출 전 10분 여유가 생긴다.

**데이터**

- ETA, 대기시간, 도착 여유, 골든타임 계산 시각, 알림 노출 여부를 저장한다.

## 요구사항 3. 원클릭·음성 승인 및 원격 줄서기 접수

골든타임에 노출된 단일 승인 카드를 운전자가 터치 또는 음성으로 승인하면 중계 서버를 통해 매장 대기열에 접수하는 기능 영역이다.

### 기능 3.1 단일 승인 카드 및 원격 웨이팅 접수

골든타임 도달 시 대형 단일 승인 카드에 매장명, 인원, 예상 대기를 보여주고 승인하면 중계 서버를 통해 접수한다. 접수 후 순번 확인을 포함한다.

**기능의 근거**: 주행 중 여러 단계의 조작은 위험하므로 한 번의 승인으로 접수를 끝내야 한다.

**성공 기준**: 승인 완료까지 걸리는 시간, 승인 성공률, 접수 오류율을 측정한다.

#### 개발 준비 슬롯

**선행조건**

- 골든타임 알림이 노출되어야 한다.
- 탑승 인원이 확정되어 있어야 한다.

**트리거**

- 운전자가 승인 버튼을 누르거나 음성으로 승인한다.

**동작**

- 승인 요청을 중계 서버에 전송한다.
- 서버가 매장 웹 POS 대기열에 팀(인원수 포함)을 접수한다.
- 접수 번호와 순번을 차량 앱에 반환한다.

**결과**

- 원격 웨이팅이 접수되고 순번과 예상 입장 시각이 표시된다.

**예외**

- 접수 실패 시 사유를 안내하고 재시도 또는 건너뛰기를 제안한다.
- 응답이 없으면 일정 시간 후 카드를 닫고 재알림 여부를 결정한다.

**표시**

- "지금 A 맛집(4명) 웨이팅을 등록할까요?" 형태의 대형 단일 승인 카드를 표시한다.

**권한 & 접근**

- 운전자가 승인한다. 주행 중 화면 승인은 플랫폼 주행 규제가 허용하는 범위에서만 제공하고 음성 승인을 우선한다.

**비즈니스 규칙**

- 사용자 승인 없이 자동으로 줄서기를 접수하지 않는다.

**데이터**

- 접수 요청, 매장, 인원수, 승인 방식, 접수 번호, 순번, 접수 시각을 저장한다.

## 요구사항 4. 주행 중 정체·대기열 변동 대응 (보조)

주행 중 도착 지연이나 매장 대기열 급변으로 도착 전 호출 또는 도착 후 대기 위험이 감지되면 안전한 원클릭·음성 UX로 순번 조정이나 경유지 순서 변경을 제안하고 실행하는 기능 영역이다. 순번 미루기는 기존 서비스에도 있어 차별 기능이 아니라 안정성을 위한 보조 기능이다.

### 기능 4.1 도착 지연·대기열 변동 감지 및 일정 재조정 제안

onTripInfo로 받은 남은 ETA의 변화량과 매장 대기시간 변화를 재계산해 도착 전 호출 또는 도착 후 대기 위험을 판단하고 영향과 대안을 안내한다. 대안 실행은 다음 기능에서 다룬다.

**기능의 근거**: 도착이 늦어지거나 대기열이 급변하면 운전 중 직접 판단하기 어렵고 노쇼 처리 위험이 있다.

**성공 기준**: 변동 감지 후 안내까지 지연 시간과 노쇼(자동 취소) 발생률을 측정한다.

#### 개발 준비 슬롯

**선행조건**

- 웨이팅이 접수되었거나 골든타임 계산이 진행 중이어야 한다.

**트리거**

- 남은 ETA가 기준 이상 늘어난다.
- 매장 대기시간이 기준 이상 급감한다.

**동작**

- ETA 변동량과 대기 변동량을 재계산해 위험을 판단한다.
- 위험 수준에 따라 대안(순번 미루기, 경유지 변경)을 구성한다.

**결과**

- 변동 원인, 영향, 대안이 담긴 제안 카드가 생성된다.

**예외**

- ETA를 수신하지 못하면 마지막 값 기준으로 판단하고 정확도 저하를 표시한다.

**표시**

- "도착이 15분 지연됩니다" 같은 요약과 대안 버튼을 표시한다.

**권한 & 접근**

- 운전자가 제안을 확인하며 음성 안내를 함께 제공한다.

**비즈니스 규칙**

- 변경 기준값(예: ETA 10분 이상 변동)은 설정으로 관리한다.
- 정체를 직접 알려주는 별도 이벤트가 확인되기 전까지는 ETA 변화량으로 감지한다.

**데이터**

- ETA 변동 이력, 대기열 변동, 위험 판단 결과를 저장한다.

### 기능 4.2 순번 미루기·차순위 경유지 선방문 실행

변동 제안에 대해 운전자가 승인하면 대기 순번을 뒤로 미루거나, 대기가 없는 차순위 경유지를 먼저 방문하도록 requestRouteWithWaypoints()를 재호출해 순서를 갱신한다.

**기능의 근거**: 승인 후 곧바로 일정이 갱신되어야 운전 중에도 노쇼 없이 일정을 지킬 수 있다.

**성공 기준**: 제안 수락률, 재경로 반영 성공률, 변경 후 입장 대기시간을 측정한다.

#### 개발 준비 슬롯

**선행조건**

- 변동 제안 카드가 노출되어 있어야 한다.
- 내비 경로 안내가 진행 중이어야 한다.

**트리거**

- 운전자가 순번 미루기 또는 차순위 경유지 선방문을 승인한다.

**동작**

- 순번 미루기 승인 시 중계 서버를 통해 매장 대기열 순번을 뒤로 조정한다.
- 경유지 변경 승인 시 순서를 재계산해 requestRouteWithWaypoints()를 재호출한다.
- 변경 결과를 골든타임 계산에 반영한다.

**결과**

- 웨이팅 순번 또는 경유지 순서가 갱신된다.

**예외**

- 순번 조정이 거절되면 기존 순번을 유지하고 안내한다.
- 재경로 요청이 실패하면 기존 경로를 유지한다.

**표시**

- 변경 전후 순서와 예상 도착·입장 시각을 표시한다.

**권한 & 접근**

- 운전자가 승인한다. 주행 중에는 단일 승인만 허용한다.

**비즈니스 규칙**

- 사용자 승인 없이 경유지 순서나 순번을 바꾸지 않는다.

**데이터**

- 변경 요청 유형, 승인 방식, 변경 전후 순서, 결과 상태를 저장한다.

## 요구사항 5. 차량·음성·주행 안전 통합 경험

Gleo 음성 인터페이스와 플랫폼 주행 규제 상태(CarUxRestrictions)를 활용해 운전자가 시선을 분산하지 않고 서비스를 사용하도록 하는 기능 영역이다.

### 기능 5.1 Gleo 음성 인터페이스 연동

Gleo App Schema의 optimizeDailyRoute, registerGoldenTimeWaiting, checkWaitingStatus 함수로 주행 중 핸즈프리 코스 정렬, 골든타임 웨이팅 음성 승인, 남은 순번 브리핑을 수행한다. 함수는 최대 3개이며 schema.json 제출과 검수 승인이 필요하다.

**기능의 근거**: 주행 중에는 화면 조작보다 음성이 안전하다.

**성공 기준**: 음성 명령 인식 성공률과 음성 승인으로 완료된 접수 비율을 측정한다.

#### 개발 준비 슬롯

**선행조건**

- assets/schema.json이 제출되어 검수 승인을 받아야 한다. 승인 전에는 화면 승인으로 같은 흐름을 시연한다.

**트리거**

- 사용자가 코스 정렬, 웨이팅 승인, 순번 확인을 음성으로 요청한다.

**동작**

- optimizeDailyRoute로 코스를 정렬한다.
- registerGoldenTimeWaiting으로 골든타임 웨이팅 승인을 처리한다.
- checkWaitingStatus로 남은 순번과 예상 입장 시각을 안내한다.

**결과**

- 음성 명령이 기능 실행 결과와 음성 응답으로 이어진다.

**예외**

- 인식에 실패하면 재요청하거나 화면 승인으로 전환한다.
- 진행 중인 웨이팅이 없으면 없다고 안내한다.

**표시**

- 음성 실행 결과를 화면 카드에도 함께 표시한다.

**권한 & 접근**

- 운전자와 동승자가 음성 명령을 사용할 수 있다.

**비즈니스 규칙**

- 음성 승인은 화면 승인과 같은 단일 승인 규칙을 따른다.
- TextToSpeech SDK는 준비 중이므로 음성 응답은 Gleo가 제공하는 범위에서 구현한다.

**데이터**

- 음성 명령 유형, 인식 결과, 실행 결과, 시각을 저장한다.

### 기능 5.2 주행 규제 기반 안전 UX

플랫폼이 제공하는 CarUxRestrictions(CarUxRestrictionsManager의 registerListener, onUxRestrictionsChanged, isRequiresDistractionOptimization)로 주행 규제 상태를 확인해, 규제 중에는 입력 조작을 잠그고 음성 승인과 최소 조작의 단일 승인 카드만 제공한다. 앰비언트 라이트는 차량 제어 SDK를 사용할 수 있을 때만 쓰는 선택 기능이다.

**기능의 근거**: Pleos 주행 규제는 속도, 기어, 브레이크 신호와 지역 규제를 기준으로 적용되며, 앱은 이를 따라야 심사를 통과한다.

**성공 기준**: 규제 중 허용되지 않은 조작 시도 차단율과 규제 중 조작 횟수를 측정한다.

#### 개발 준비 슬롯

**선행조건**

- CarUxRestrictionsManager로 상태를 받을 수 있어야 한다.
- 앱 카테고리와 DO 선언 범위가 확정되어야 한다.

**트리거**

- 주행 규제 상태가 변경된다.
- 골든타임이나 변동 알림이 발생한다.

**동작**

- 규제 상태에 따라 입력 중심 UI를 잠그고 단일 승인 카드와 음성만 활성화한다.
- 기어 상태를 읽을 수 있으면 보조 조건으로만 사용한다. (getCurrentGearSelectionState는 deprecated)
- 앰비언트 제어가 가능한 환경에서만 부드러운 앰비언트 알림을 추가한다.

**결과**

- 상태에 맞는 UI 제한과 알림이 적용된다.

**예외**

- 상태를 읽지 못하면 안전을 위해 규제 중으로 간주해 제한을 유지한다.
- 앰비언트 제어가 불가능하거나 실패하면 화면·음성 알림만 제공한다.

**표시**

- 규제 중에는 대형 글자와 최소 정보만 표시한다.

**권한 & 접근**

- 정차 중에만 설정과 코스 편집을 허용한다.

**비즈니스 규칙**

- 규제 중 조작 제한은 사용자 설정으로 해제할 수 없다.
- DrivingMode(주행 모드·크루즈 정보)는 정차 판별에 쓰지 않는다.

**데이터**

- 규제 상태 이력, 알림 발생 및 선택 기능 제어 결과를 저장한다.

## 요구사항 6. 매장 웹 POS 연동, 도착·하차 확인 및 데이터·동의 관리

매장 점주용 웹 POS(태블릿)와 차량 앱의 실시간 대기열 양방향 연동, 차량 신호 기반 도착·하차 확인, 외부 전송 항목의 고지와 동의 관리를 다루는 기능 영역이다.

### 기능 6.1 매장 웹 POS 대기열 연동

FastAPI·WebSocket 중계 서버로 매장 웹 POS와 차량 앱의 대기열을 양방향 실시간 동기화한다. 점주는 접수 팀의 인원, 차량 ETA, 도착·하차 현황을 보고 호출한다.

**기능의 근거**: 상용 웨이팅 플랫폼이 공개 API를 제공하지 않아 자체 웹 POS가 있어야 실제 동작 시연과 노쇼 방지가 가능하다.

**성공 기준**: 차량 앱과 웹 POS 간 동기화 지연 시간과 도착 후 대기 0분 입장 비율을 측정한다.

#### 개발 준비 슬롯

**선행조건**

- 중계 서버와 웹 POS가 연결되어 있어야 한다.

**트리거**

- 점주가 웹 POS에서 대기 팀 수나 순번을 변경한다.
- 차량 앱이 접수, 인원 변경, 도착·하차 정보를 전송한다.

**동작**

- WebSocket으로 대기열 변경을 차량 앱에 실시간 전달한다.
- 웹 POS에 접수 팀의 인원, 차량 ETA, 도착·하차 현황을 표시한다.
- 호출 시 차량 앱에 번호표 QR을 반환한다.

**결과**

- 대기열 변경이 양쪽에 반영되고 도착 후 즉시 입장이 가능하다.

**예외**

- 네트워크 단절 시 마지막 상태를 유지하고 복구 후 재동기화한다.
- 도착 후 호출이 지연되면 대기 상태를 표시한다.

**표시**

- 웹 POS에는 인원, ETA, 도착·하차 현황을 표시하고 차량에는 번호표 QR을 표시한다.

**권한 & 접근**

- 점주는 웹 POS에서 대기열을 관리하고 운전자는 자신의 순번만 조회한다.

**비즈니스 규칙**

- 차량 신호로 도착·하차가 확인된 웨이팅은 매장에서 우선 고객 채널로 표시한다.

**데이터**

- 매장, 대기 팀, 순번, ETA, 도착 상태, 하차 인원, 입장 QR 정보를 저장한다.

### 기능 6.2 차량 신호 기반 도착·하차 확인 (핵심 차별 기능)

도착 이벤트, 정차 상태, 도어 열림·닫힘, 접수 인원 대비 좌석 점유 감소를 종합해 "N명 중 M명 하차 확인"을 웹 POS에 자동 전달한다. 인원 수 확인이며 신원 인증이 아니다.

**기능의 근거**: 폰은 위치 인증이나 코드 입력으로만 도착을 확인하고 실제 몇 명이 왔는지 알 수 없다. 차량은 도착, 도어, 좌석 변화로 이를 자동 확인할 수 있다.

**성공 기준**: 하차 확인 정확도(시나리오 테스트 통과율), 수동 "도착했어요" 전환 비율, 도착 후 대기 0분 입장 비율을 측정한다.

#### 개발 준비 슬롯

**선행조건**

- 웨이팅이 접수되어 있어야 한다.
- CAR_SEATS, CAR_DOORS 권한이 선언되어 있고 좌석 점유와 도어 위치 기능을 지원하는 차량이어야 한다. (checkSeatOccupancyCapabilities, checkDoorPositionCapabilities로 확인)
- 외부 전송 동의가 완료되어 있어야 한다.

**트리거**

- onDestinationArrived 또는 onWayPointArrived를 수신한다.

**동작**

- 도착 이벤트 수신 후 주행 규제 상태(CarUxRestrictions)로 정차를 확인한다. 기어 상태를 읽을 수 있으면 보조 조건으로 쓴다.
- registerDoorPosition으로 도어 열림·닫힘을 수신한다.
- 좌석 점유 수가 접수 인원 대비 줄어드는지 확인한다. 하차 인원은 접수 인원에서 현재 점유 수를 뺀 값으로 추정한다.
- 조건이 안정화 시간(초) 동안 유지되면 전송 직전에 도어와 좌석 값을 다시 읽어 확인한다.
- "N명 중 M명 하차 확인"을 중계 서버로 전송한다.

**결과**

- 웹 POS에 "도착, M/N명 하차, 입장 가능"이 표시되고 점주가 호출한다.

**예외**

- 센서 미지원이나 값 불일치, 상태 불명확 시 확정하지 않고 정차 중 "도착했어요" 버튼 한 번으로 대체한다.
- 점유가 잠깐 흔들린 것만으로 확정하지 않는다.
- 운전자가 차에 남는 경우를 고려해 인원 기준(M/N)으로만 표시한다.

**표시**

- 차량에는 "하차 확인: M/N명"을 표시하고, 웹 POS에는 도착과 하차 현황을 표시한다.

**권한 & 접근**

- 운전자가 정차 중 수동 확인 버튼을 사용할 수 있다. 점주는 결과만 조회한다.

**비즈니스 규칙**

- 하차 확인은 인원 수만 전달하며 신원 정보와 보안 용도로 쓰지 않는다.
- 확정되지 않은 상태를 성공으로 표시하지 않는다.

**데이터**

- 도착 이벤트 시각, 도어 상태, 점유 수 변화, 안정화 시각, 확정 인원, 수동 전환 여부를 저장한다.

### 기능 6.3 외부 전송 고지 및 동의

ETA, 탑승 인원, 하차 인원, 도착 여부, 웨이팅 정보가 클라우드 서버와 매장 웹 POS로 전송되기 전에 전송 항목과 목적을 고지하고 동의를 받으며 철회할 수 있게 한다. 위치 좌표와 이동 궤적은 전송하지 않는다.

**기능의 근거**: 인원·도착 정보가 외부로 전달되므로 고지·동의와 데이터 최소화가 필요하다.

**성공 기준**: 동의 완료율, 철회 처리 시간, 개인정보 관련 오류 건수를 측정한다.

#### 개발 준비 슬롯

**선행조건**

- 외부 전송이 필요한 기능을 처음 사용하는 경우여야 한다.

**트리거**

- 사용자가 서비스를 처음 실행하거나 전송 항목이 변경된다.

**동작**

- 전송 항목, 수신처, 목적을 정차 중 고지한다.
- 동의 여부를 저장하고 동의 시에만 외부 전송을 시작한다.
- 철회 시 이후 전송을 중단한다.

**결과**

- 동의한 범위에서만 데이터가 전송된다.

**예외**

- 동의하지 않으면 외부 연동 기능을 사용할 수 없음을 안내한다.

**표시**

- 전송 항목, 목적, 수신처를 쉬운 문구로 표시한다.

**권한 & 접근**

- 운전자가 정차 중 동의하고 설정에서 철회할 수 있다.

**비즈니스 규칙**

- 동의 없이 인원·도착 정보를 외부로 전송하지 않는다.

**데이터**

- 동의 항목, 동의·철회 시각, 고지 문구 버전을 저장한다.

# 3. 프로덕트 정책

## 정책 1. 골든타임 산정 및 웨이팅 시점 규칙

- 골든타임은 남은 ETA가 (매장 예상 대기시간 − 도착 여유)에 도달하는 시점이다. 접수 후 호출이 도착 직후에 오도록 하기 위함이다.
- 도착 여유 기본값은 10분이며 매장별로 조정할 수 있고, ETA·대기시간이 바뀔 때마다 재계산한다.
- 예시: 이동 60분, 대기 30분이면 남은 ETA가 20분이 되는 시점(출발 40분 후)에 승인 카드를 노출한다. 접수 30분 뒤 호출되고 도착은 20분 뒤이므로 10분 여유가 생긴다.
- 이동 시간이 이미 (대기시간 − 도착 여유)보다 짧으면 즉시 알린다.
- ETA 또는 대기시간을 수신하지 못하면 마지막 값을 사용하고 정확도 저하를 표시한다.

연결된 기능: 2.1, 3.1, 4.1

## 정책 2. 사용자 승인 및 단일 승인 원칙

- 원격 줄서기 접수, 인원 변경, 순번 미루기, 경유지 순서 변경은 사용자 승인 없이 자동 실행하지 않는다.
- 승인은 대형 단일 카드에서 한 번의 터치 또는 음성으로 완료되어야 한다.
- 음성 승인(Gleo)과 화면 승인은 같은 규칙을 적용한다.
- 승인 없이 일정 시간이 지나면 카드를 닫고 재알림 여부를 별도 규칙으로 판단한다.

연결된 기능: 1.3, 3.1, 4.2, 5.1

## 정책 3. 주행 안전(Driver Distraction) 및 UI 잠금 정책

- 주행·정차 판별은 플랫폼의 CarUxRestrictions 상태를 기준으로 한다. 상태를 읽지 못하면 규제 중으로 간주한다.
- Vehicle SDK의 DrivingMode는 주행 모드·크루즈 정보라 정차 판별에 쓰지 않는다. 기어 조회는 deprecated이므로 보조 조건으로만 쓴다.
- 규제 중에는 코스 설정, 인원 수정, 설정 변경 등 입력 중심 조작을 잠그고 음성 승인과 최소 조작의 단일 승인 카드만 제공한다.
- 주행 중 사용 가능 범위는 Pleos 주행 규제 정책과 앱 카테고리, DO 선언에 따라 달라지므로 공식 기준으로 확정하고, 허용 범위가 좁으면 음성 승인만 제공한다.
- 규제 중 화면은 대형 글자와 최소 정보만 표시한다.
- 앰비언트 라이트는 선택 기능이며 차량 제어 SDK를 사용할 수 없거나 실패하면 화면·음성 알림만 제공한다.
- 규제 중 조작 제한은 사용자 설정으로 해제할 수 없다.

연결된 기능: 5.2, 5.1, 3.1

## 정책 4. 위치·인원 정보 외부 전송 및 개인정보 정책

- 클라우드 중계 서버와 매장 웹 POS로 전송하는 항목은 ETA, 탑승 인원, 하차 인원, 도착 여부, 웨이팅 정보로 제한한다. 위치 좌표와 이동 궤적은 전송하지 않는다.
- 전송 항목, 수신처, 목적을 정차 중 고지하고 동의를 받는다. 동의 없이는 외부 전송을 시작하지 않으며 설정에서 언제든 철회할 수 있다.
- 매장 점주에게는 접수 팀의 인원, ETA, 도착·하차 현황만 제공한다.
- 동의·철회 시각과 고지 문구 버전을 기록한다.
- 하차 확인은 인원 수만 다루며 신원 인증이나 보안 용도로 쓰지 않는다.

연결된 기능: 6.3, 1.1, 6.1, 6.2

## 정책 5. 외부 연동 범위 및 SDK 가용성 정책

- 캐치테이블·테이블링 등 상용 웨이팅 플랫폼은 공개 API가 없어 직접 연동하지 않는다.
- 대신 차량용 앱(Pleos Connect) ↔ 클라우드 중계 서버(FastAPI + WebSocket) ↔ 매장 점주용 웹 POS(React, 태블릿)의 3-Tier 구조로 실시간 대기열을 양방향 연동한다.
- 경로·시간 계산은 카카오모빌리티 다중 경유지 API와 SK T MAP 경유지 API를 사용하고 requestRouteWithWaypoints()로 순정 내비에 반영한다. 경유지는 최대 2개이므로 코스는 최대 3곳이다.
- Vehicle State(좌석, 도어)와 NaviHelper SDK(v3.0.5)는 신청 없이 사용할 수 있다. 필요 권한은 NAVI_ROUTE, NAVI_ROUTE_SEARCH, CAR_SEATS, CAR_DOORS, INTERNET이다.
- 차량 제어(Vehicle Control) SDK와 TextToSpeech SDK는 현재 준비 중이므로 핵심 기능에서 제외하고, 사용 가능해질 때 선택 기능으로 적용한다.
- Vehicle SDK 지원 여부는 차량 모델에 따라 다르므로 모델명으로 분기하지 않고 checkXXXCapabilities로 확인한다.
- 음성 연동은 Gleo App Schema 함수 3개(optimizeDailyRoute, registerGoldenTimeWaiting, checkWaitingStatus)로 제한하며 schema.json 제출과 검수가 필요하다.

연결된 기능: 6.1, 1.2, 5.1, 6.2

## 정책 6. 가맹점(B2B) 및 수익 모델 정책

- 스마트 저니를 통해 접수된 웨이팅은 차량이 도착과 하차 인원을 확인한 방문으로 표시해 노쇼를 줄이고 테이블 준비를 돕는다. 예약금은 요구하지 않는다.
- 초기에는 로컬 인기 매장에 경량 웹 POS를 무상 보급해 가맹점을 확보한다. 이후 수익은 접수 건당 수수료 또는 월 구독 중 하나를 파일럿 결과로 결정하며 요율은 정하지 않았다.
- 가맹점 확보 전략: 인기 매장 몇 곳과 시범 운영하고 노쇼 감소 효과를 먼저 보여 확산한다.
- 확장 방향: 전기차 급속 충전소 대기열 예약(EV 배터리 도메인 활용 검토), 백화점·호텔 발렛 출차 준비, 드라이브스루 ETA 기반 조리 시작.

연결된 기능: 6.1, 6.2

## 정책 7. 도착·하차 확인 정책

- 도착 이벤트 수신 후 정차 확인, 도어 열림·닫힘, 접수 인원 대비 좌석 점유 감소를 모두 만족하고 안정화 시간(초) 동안 유지될 때만 "N명 중 M명 하차 확인"을 확정한다.
- 확정 직전에 도어와 좌석 값을 다시 읽어 확인한다.
- 값이 모호하거나 센서를 읽지 못하면 확정하지 않고 정차 중 "도착했어요" 버튼으로 전환한다.
- 운전자가 주차를 위해 차에 남을 수 있으므로 인원 기준(M/N)으로만 표시한다.
- 하차 확인은 인원 수 확인이며 신원 인증이 아니다.

연결된 기능: 6.2, 6.1, 1.1
